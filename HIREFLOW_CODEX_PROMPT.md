## 2. Product and architecture

Ship a single-company recruitment MVP for a Software & IT company. Build three internal areas for Jobs, Candidates and Interviews. Add staff login/recovery, public application and private booking pages. Candidates apply without accounts. Postgres is the source of truth. The web server owns authorization, state transitions and recording human decisions. n8n executes background work and reports outcomes through authenticated, narrowly scoped APIs. Browsers never call n8n. The web app does not need a Gemini key, Gmail OAuth tokens, Calendar credentials or an OpenAI API key.

Use Next.js App Router, TypeScript in strict mode, Tailwind, accessible UI components (shadcn/ui where helpful), Supabase Auth/PostgreSQL/Private Storage and Zod boundary schemas. Keep a single web codebase plus a small independently runnable outbox dispatcher. Reuse a compatible existing stack when appropriate and document material differences. Pin compatible maintained dependencies in a lockfile. Separate page rendering, input validation, business rules and data access sufficiently to test them. Enforce multi-record invariants in Postgres transactions, for example through narrowly granted SQL functions.

The initial scope excludes multi-tenancy, offers, tasks, payroll, WhatsApp, RAG, advanced analytics, automated technical assessments of applicants and automated hiring decisions. The Jobs screenshot guides layout. Use its sidebar, light background, table density, status pills, tab counts, primary button and responsive hierarchy. Render functioning controls backed by data. Use dashboard summaries only if they serve an existing task. Leave out filled-position counts unless an agreed data source exists.

## 4. Data model and invariants

Use SQL migrations, UUIDs for public identifiers, foreign keys, state checks, useful indexes and server-generated timestamps. Keep the web/API path authoritative for protected state transitions. Grant staff only the DB operations those paths actually require. The five business tables from the handoff remain recognizable. Add support tables where needed to implement a specific invariant.

| Entity | Minimum responsibility |
|---|---|
| jobs | Unique stable job_code, title, description, required/preferred skills, experience, status, requirements_version, timestamps. |
| candidates | Internal person identity and normalized contact lookup. A matching email helps identify a record and grants no access. Public submissions cannot rewrite existing profiles or old applications. |
| applications | candidate_id, job_id, source, source_external_id, submitted contact snapshot, immutable CV object reference, privacy provenance, processing/review states, timestamps. job_id can be null only for unmatched intake. Preserve CV and analysis per application. |
| interviews | application, interviewer, slot, start/end as timestamptz, IANA timezone, state, schedule revision, provider calendar/event IDs and safe Meet link. One active interview per application in this MVP. |
| notifications | application/interview link, type, dedupe_key, state, attempts, provider ID, sent_at and sanitized error. |
| Supporting records | Staff membership/role, analysis runs and immutable snapshots, booking invitations, interviewer slots, durable integration events and an append-only record of material business transitions. Keep these small. |

Capture the actual job requirements at form acceptance or Gmail assignment in the same transaction that creates the analysis run. A retry uses the same snapshot. An explicit reanalysis against changed requirements creates a new run and preserves prior evidence. Only the active run can update the current result. Require a scoped unique external intake key and a unique notification dedupe key. Track the active run ID and schedule revision with conditional writes. Prevent overlapping active reservations for an interviewer at database level. Store and compare UTC instants and render IANA timezones, including daylight-saving transitions.

Keep separate state machines for processing (queued, processing, completed, needs_manual_review, failed_retryable, failed_final), review (needs_job_assignment, awaiting_review, hold, interview_approved, rejected), notification delivery (pending, sending, sent, failed, unknown), and scheduling (reserved/calendar_pending, confirmed, reschedule_pending, cancel_pending, cancelled, sync_failed or equivalent). Define allowed actors and transitions centrally. A stale callback cannot reopen a cancelled appointment, undo a decision or replace a later result.

## 5. Web ↔ n8n integration

Deliver a versioned contract, shared schemas, synthetic request/response fixtures and a runnable smoke command for the automation engineer. Use the handoff routes below as the canonical integration paths. Equivalent internal organization is fine. Version payloads with schema_version. Keep errors structured (code, safe message, request_id, retryable). Document validation and 400/401/403/404/409/410/413/415/429/5xx behavior where applicable. Treat duplicate deliveries of the same successful operation as idempotent success. Reject reuse of an idempotency key with a different payload. Document idempotency scope and retention per operation.

| Caller and route | Behavior |
|---|---|
| Public · POST /api/applications | Validate the public job, contact, consent and server-issued upload handle. Atomically persist application, snapshot/run and outbox event. Return a non-sensitive receipt. If using direct uploads, provide a rate-limited upload-intent endpoint scoped to a single job, object and expiry. |
| HR · job, staff review and CV endpoints | Authorize each object/action. Implement assign-job, retry-analysis, explicit reanalysis, hold, reject and POST /api/applications/{id}/invite. Provide a short-lived authorized CV read after checking the application. |
| WF01 · POST /api/internal/intake/gmail | Accept authenticated metadata and a handle to a validated private attachment through a documented server-side ingestion flow. Never fetch an arbitrary attachment URL supplied by a client. Persist once. Choose a single owner of dispatch so a Gmail import cannot start two analyses. |
| WF01 · GET /api/internal/applications/{id}/analysis-context | Validate workflow identity and run_id. Return only the run's immutable job snapshot and temporary read access to that application's verified file. The teammate owns text extraction and OCR fallback. |
| WF01 · POST /api/internal/applications/{id}/analysis-result | Validate run, expected event/job version and strict result schema. Support success, unreadable CV/manual review and retryable/final errors. Store validated evidence history. Reject/quarantine malformed results. Handle stale or replayed callbacks. |
| WF02 · POST /api/internal/notifications/{id}/claim and /result | Only a saved human approval can release invite context. Return only an authorized recipient, email template data and the scoped booking URL. Atomically claim the logical send and record delivery, failure or uncertainty. |
| Public · GET /api/booking/{token}/slots and POST /api/interviews/book | Verify token scope/version/expiry, availability, eligibility and same-operation replay. Reserve atomically and enqueue WF03. | WF03 · GET /api/internal/interviews/{id}/sync-context and POST /api/internal/interviews/{id}/sync-result | Restrict create/update/cancel operations to the bound interview and revision. Return the authorized interviewer/calendar and times. Validate provider IDs, state and Meet URL before persistence. |
| WF04 · POST /api/internal/reminders/claim and notification result | For the teammate's scheduled run every 15–30 min, atomically claim due 24h/1h reminder intents for active, confirmed appointments. Recheck eligibility before release to send. Deduplicate by interview + schedule revision + reminder type. |

## 6. Security and privacy requirements

- **SEC01 — Access boundaries.** Verify the staff session and current server-controlled membership on every sensitive read/write. Apply deny-by-default Postgres grants, RLS and Storage policies. Use user-scoped database access when possible. Isolate privileged operations to server-only code with explicit authorization. Guard direct Supabase REST, Storage and RPC access as well as Next.js routes. Protect privileged functions (restricted execution grants and safe search_path). Include tests as anonymous, authenticated non-member, HR, Admin and integration identities. Reject modifications to server-owned fields such as role, status, candidate_id, object path or approval actor.
- **SEC02 — Uploads.** A 5 MiB file must fit the selected hosting path. If the platform's request limit is lower, issue restricted upload intents to private quarantine, then verify and finalize server-side. Enforce per-object size and bounded actual bytes, extension/type allowlists, signatures and format structure. For DOCX check required Office package members and bounded decompression (zip bombs/path abuse). For PDF avoid executing active content. Generate opaque paths, prevent overwrite, bind each verified handle to its purpose and consume it once. Clean abandoned and rejected objects. A validation failure never makes a file accessible to HR or n8n. Document the malware scanning path and gate real-data launch on an operating scanner or explicit owner-approved handling policy. Serve safe downloads or use a separate origin to display untrusted documents.
- **SEC03 — Files, secrets and personal data.** Use private bucket candidate-cvs. Store object references, never public or reusable signed links. Authorize a fresh signed URL (initial TTL five minutes) or server proxy for each read. Keep service keys and n8n secrets on servers. Use distinct keys per environment, least privileges and a documented rotation procedure. Do not send the Supabase service key to n8n. Use only synthetic people, CVs and evidence in fixtures and demo screenshots. Redact tokens, signed URLs, email bodies, CV text and personal data from logs, analytics and error reports. Include .env.example with names only. Production/staging readiness must distinguish missing setup from healthy integrations.
- **SEC04 — HTTP and abuse.** Validate and cap all inputs on the server. Parameterize queries, allowlist filters/sorts, escape output, check origins/CSRF for cookie-authenticated writes and avoid permissive CORS. Use safe session cookie settings appropriate to Supabase SSR, HTTPS in deployed environments, private/no-store for personalized responses, and verified allowed hosts for outbound/surfaced URLs. Keep upload and booking pages free of third-party analytics and token leakage. Implement shared rate limits for login/recovery, upload intents, submissions, booking and internal routes. Return useful retry information. Trust forwarded client IP only behind a configured trusted proxy.
- **SEC05 — Integration auth.** Separate web→n8n and n8n→web credentials. On inbound internal endpoints require workflow-scoped authentication. Default to HMAC-SHA256 with key ID, timestamp and method + canonical path/query + raw body digest, TLS and constant-time verification. Document the canonical form, clock-skew window and a working signing example. Reject stale signatures, unauthorized workflow scopes, mismatched object/run IDs and unsupported payload versions. Deduplicate valid retries durably at the business operation. A valid signature alone cannot change human decisions.
- **SEC06 — Booking secrets and audit.** Bind the booking capability to one invitation, interviewer and application, with expiry, revocation and one successful reservation. GET requests and email link previews cannot consume it. Use a server-signed, versioned link that can be reissued to the sender for delivery retries and whose validity is checked against DB state. Persist no reusable plaintext token in logs/outbox. Log actor, action, object ID, time and correlation ID for material transitions. Limit audit access and sensitive payloads. Implement a configurable retention/deletion procedure that handles files, analysis and derived data, preserves only justified audit facts, and retries failed cleanup. Mark production retention duration and policy text as client decisions.

## 7. Reliability, speed and scale requirements

| ID | Engineering requirement | Verification |
|---|---|---|
